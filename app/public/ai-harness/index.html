0. 최종 원칙

문제·범위·완료 기준은 사람이 소유하고, AI는 질문·대안·구현·검증을 맡는다.

모델 운영: 가장 빠른 충분한 모델로 시작하고, 위험·불확실성이 커질 때만 더 강한 모델과 독립 검토를 추가한다.

1. 바꾸려는 것은 '일하는 순서'다

❌ 기존 패턴

업무 불명확 → AI에 긴 자료 전체 전달 → AI가 기획·범위까지 생성
→ 바로 구현 → 결과물 비대화 → 설명 불가 → 대규모 수정 → 야근

문제는 AI를 많이 쓴 게 아니라, 문제 정의와 범위 결정까지 AI에게 넘긴 것이다.

✅ 새 구조

사람: 문제·사용자·완료 기준 결정
 AI : 질문·대안·위험 제시
사람: 범위와 방법 선택
 AI : 구현
 AI : 독립 검증 (가능하면 다른 계열 모델)
사람: 결과를 설명하고 최종 판단

2. 작업 시작 전 — 5줄 기획 카드

AI에게 넘기기 전에 반드시 직접 작성한다. 완벽할 필요 없이 5줄이면 된다.

문제: 지금 무엇이 불편하거나 잘못됐는가?
사용자: 누가 이것을 사용하는가?
판단: 사용자가 무엇을 알거나 결정할 수 있어야 하는가?
이번 범위: 이번에 어디까지만 할 것인가?
완료 기준: 무엇을 확인하면 끝났다고 할 것인가?

카드를 쓴 뒤 AI에게는 이렇게 요청한다:

이 기획 카드에서 빠진 전제와 위험을 찾아줘.
확정되지 않은 값을 추정하지 말고 질문으로 분리해줘.
구현안은 최대 2개만 제시하고 장단점을 비교해줘.
아직 코드는 작성하지 마.

→ AI가 기획을 대신하는 게 아니라 검토하는 역할이 된다.

3. 작업 모드 판단

요청을 받으면 어느 모드인지 먼저 판단하고 명시한다.

⚡ 빠른 모드 — 단순하고 되돌리기 쉬운 작업

  • 예: 문장 정리, 요약, 파일 분류, 오탈자, 형식 변환
  • 진행: 모델 1개, 질문 최소화, 바로 결과
  • 검토: 불필요 (여기에 다중 모델 검토는 오히려 낭비)

📋 표준 모드 — 일반 분석·개발 작업

  • 예: 요구사항 구조화, 화면 구성안, 기능 추가, 리팩터링
  • 진행: 기획 확인 → 모델 1개 구현 → 테스트
  • 검토: 필요시 다른 관점 반론 1회

🔒 중요 모드 — 운영·보안·판정·고객 결과물

  • 예: 배포, 판정 로직, 임계값 적용, 데이터 삭제·이동, 고객용 최종 산출물
  • 진행: 기획 카드 → 사람 결정 → 구현 → 다른 계열 모델 독립 검토 → 테스트 → 사람 승인 후 실행
  • 승인 지점: 기획 승인 → 구현 → 테스트 확인 → 배포 승인 → 배포 → 원격 검증

위험도 × 명확성 매트릭스

명확불명확
저위험바로 처리AI가 질문·대안 정리 → 사람 결정
고위험구현 + 독립 검토구현 중단 → 기획 카드 → 사람 결정 → 구현 + 타 모델 검증

⚠️ 고위험·불명확에서 강한 모델은 해결책이 아니다. 어떤 모델이든 모르는 정보(매핑, 임계값 출처, 실제 사용자, 배포 범위)를 그럴듯하게 추정할 수 있다. 이때 필요한 건 모델 승격이 아니라 정보 확보와 사람의 결정이다.

4. 중단 조건 — 감지되면 구현을 멈춘다

🛑 조건 1: 목적을 한 문장으로 설명할 수 없음

"이 기능으로 누가 무엇을 판단하는가?"에 답이 없으면 → 먼저 기획한다.

🛑 조건 2: 사실과 가설이 섞임

실제 확인된 값 / 계산값 / AI 제안 기준 / 현장 확인 필요 — 분리한 뒤 진행한다.

🛑 조건 3: 원래 요청보다 범위가 커짐

원 요청만 처리하고 나머지는 제안으로 돌린다.

🛑 조건 4: 결과를 설명하기 어려움

구현 뒤 다음을 설명할 수 있어야 한다 — 왜 만들었나 / 입력 데이터 / 계산 기준 / 미확인 사항 / 검증 방법. 설명이 어려우면 결과를 더 만들지 말고 먼저 구조를 다시 설명한다.

🛑 조건 5: 야근으로 범위를 메우려 함

시간 부족 시 순서: 범위 축소 → 중간 결과 공유 → 미확인 사항 명시 → 후속 단계 분리.

5. AI와 일할 때의 약속

  1. 큰 요청은 바로 구현하지 않고 먼저 목적·범위·완료 기준을 구조화해서 보여준다. (목적 / 확인된 사실 / 미확인 사항 / AI가 제안한 해석 / 이번 범위 / 하지 않을 것 / 완료 기준)
  2. 확인된 사실 · 사용자 결정 · AI 제안 · 미확인 사항을 항상 분리해서 표기한다.
  3. 사용자가 결정해야 할 것을 AI가 사실처럼 확정하지 않는다.
  4. 질문은 결과가 실제로 달라지는 핵심 질문만 한다. 저위험 결정(색상, 오탈자)은 합리적 기본값으로 처리한다.
  5. 선택지는 최대 2개 + 권장안 + 이유로 제시한다. 열 가지 나열 금지.
  6. 구현 중 더 좋은 아이디어를 발견해도 합의된 범위에 몰래 추가하지 않는다.
  7. 작은 작업은 빠르게 처리한다. 불필요한 다중 검토로 속도를 죽이지 않는다.
  8. 구현 뒤 사용자가 설명할 수 있도록 계산·데이터·코드 흐름을 정리해서 전달한다.
  9. 배포·삭제·운영 변경은 반드시 별도 승인을 받는다.
  10. 범위가 커지거나 근거 없는 임계값이 필요해지면 즉시 멈춘다.

6. 결과 평가 기준

응답이 빨랐다고 좋은 작업이 아니다. 기록할 것:

  • 첫 결과까지 시간 / 전체 완료 시간
  • 요구사항 일치 여부 / 테스트 통과 여부
  • 재작업 횟수 / 추정·환각 발생 여부
  • 내가 설명할 수 있는가 ← 가장 중요
  • 비용·구독 한도

결과는 나왔지만 내가 설명할 수 없는 작업 = 완성도가 낮은 작업.
